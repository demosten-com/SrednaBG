# android/core/

Pure Kotlin library (no Android deps) with zone detection, average speed calculation, GPS filtering, geo utilities, map-theme resolution, and zone-status colors. The iOS port at `ios/Packages/SrednaBGCore/` is an independent Swift hand-port of this engine and evolves separately. 9 source files + 11 test files (including real Trakiya zone fixtures).

- `ZoneDetector` (stateful) — receives GPS points, self-orients each centerline `start → end` at construction, detects zone entry/exit via point-to-polyline distance + heading match (±45°)
- `AverageSpeedCalc` — running average + `SpeedStatus` (max speed sustainable for the remainder, `isOverLimit`)
- `GpsFilter` — Kalman-like noise smoothing
- `RoadMatcher` — road/direction matching
- `GeoUtils` — Haversine, bearing, polyline distance
- `VehicleType` — `CAR`/`TRUCK`/`BUS`/`MOTORCYCLE` enum with per-vehicle `limit(speedLimits)` selection. These are BG TOLL **licence categories, not vehicle shapes** — `BUS` is the whole `BE,C1,C1E,D,D1,D1E,DE` class, so a car towing a trailer selects it too
- `MapThemeResolver` — picks the light or dark MapLibre style URI for a given setting + system appearance
- `ZoneStatusColor` — packed-`Int` mapping from `ZoneState` / over-limit flag to the green / amber / red traffic-light value used by both the SwiftUI and UIKit/Compose surfaces, plus `ZONE_COLOR_NEUTRAL` for `ZoneState.Unmeasured` (which gets no verdict)

## The four zone states

`ZoneState` is `Outside | Unmeasured | InZone | Exiting`. The one that isn't obvious is **`Unmeasured`**: inside a zone whose entry we did **not** witness, so no measurement is possible. See "Entry provenance" below for the rule that produces it. Two invariants the whole design leans on, stated in `Models.kt`:

- **`Exiting` only ever follows `InZone`.** An `Unmeasured` zone has no traversal to finalize, so leaving one goes straight to `Outside`. That is what keeps a mid-zone join out of History and out of the exit announcement with **no** suppression logic at any consumer — `HistoryRecorder` treats `Unmeasured` exactly like `Outside`, and nothing ever hands it a traversal to close.
- **`Unmeasured → InZone` is unreachable for the same zone.** `handleUnmeasured` returns only `Unmeasured` or `Outside`, and arc length only increases, so a start cannot be witnessed retroactively.

`Unmeasured` carries the zone (hence its speed limit) and `distanceRemaining` — facts about the road, true regardless of when we joined — and **structurally** nothing derived from timing or averaging: there is no average to accidentally render. Consumers show zone + limit + distance-left + live speed in a neutral colour, and say nothing.

## Algorithm edge cases

- **Stop detection**: speed < 5 km/h for > 30s → pause timing (rest areas, traffic)
- **GPS dropout**: gap ≥ 10 s → the speed×time integrator has no samples to work with, so distance is **bridged from the centerline projection** (`arcNow - arcPrev`) instead. Dropping the gap outright (the old behaviour) left `elapsed` counting time the numerator never got credit for and deflated the reported average — a real ~15 s dropout turned an ~87 km/h drive into a reported **24 km/h** (`travelSince`; regression `ZoneDetectorTest."GPS dropout does not deflate the reported average"`)
- **Entry confirmation (anti-phantom)**: a zone does **not** open on the first fix that lands in the on-road band. The match must hold while the vehicle covers `ENTRY_CONFIRM_DISTANCE_M` (300 m, capped at `ENTRY_CONFIRM_MAX_FRACTION` = 25 % of a short zone) of travel **along the centerline**, over at least `ENTRY_CONFIRM_FIXES` (2) fixes — the mirror of the off-road exit grace. Roads that merely cross or run alongside a zone sit inside the band on a plausible heading for a few hundred metres: the A3 Струма motorway passes within ~7 m of the I-1 centerline for ~190 m at the Кочериново interchange, which used to open a *full* phantom traversal of the 10.6 km `i1-02-north` zone for motorway traffic (entry announcement + junk History record, then an exit 13–21 s later; user-reported from a real drive, seen identically on both platforms). The confirmed traversal is **back-dated** to the candidate's first fix — its timestamp and the ground covered since — so the window costs announcement latency, never averaging accuracy. A candidate that goes quiet for `ENTRY_CONFIRM_TIMEOUT_MS` (30 s) or switches zone restarts. Regressions: `ZoneDetectorTest."road clipping the band on a matching heading never opens a traversal"` + `"…still enters, back-dated to the first fix"`, `qa/scenarios/edge/parallel_motorway.py` (replays the real A3 geometry)
- **Entry provenance (`START_WITNESS_ARC_M` = 200 m)**: confirmation proves we have been *on this road*, not that we saw the driver pass the entry camera. So a confirmed candidate opens a measured `InZone` traversal only when its **first** fix projected within `START_WITNESS_ARC_M` of the centerline start; otherwise it opens `ZoneState.Unmeasured`. The governing principle is deliberate and settled: *if the app did not see the driver cross an entry camera it cannot produce trustworthy data and must not attempt to help — the reason it missed the entry is irrelevant.* App restart, permission granted mid-drive, tunnel, process death and a genuine late join are all treated identically, because the distinction makes no difference to the driver. This replaced the old proximity admission (`ENTRY_DISTANCE_M` = 500 m + a `midZone` cold-start branch), which presented a partial traversal — averaged over the remainder only, matching nothing BG TOLL computes — in the same chip, the same spoken phrase and the same History row as a real one (the junk 24 km/h record, real drive 2026-07-26). Proximity could not make the call: the A3 phantom's first matching fix sat 270–460 m from `zone.start`, inside the old buffer. Arc position can, because for a car genuinely approaching, the first fix that matches at all projects to arc ≈ 0.

  **The 200 m is measured, not guessed.** Across all 72 bundled zones the worst first-match arc on a legitimate approach is **121 m** at the 2 s near-zone cadence and **148 m** at the 5 s cold-start cadence — both at `i3-02-north`, whose stored centerline opens with a 121 m segment running ~180° *against* the road (ISSUE-001; `i6-01-east` 80 m and `trakiya-03-east` 77 m share it), so an approaching car snaps to the far end of that jog rather than to arc 0. The 100 m first proposed would have made those three zones report "not measured" on every real drive. 200 m clears the worst legitimate case by 1.35× and stays under the 268 m the observed A3 phantom projected to. Entry confirmation remains the primary anti-phantom defence; this constant only separates "approached the camera" from "joined deep inside". A **co-located handover counts as witnessed by construction** (`witnessedStart || handedOver`) — driving the previous zone to its end *is* crossing this one's start camera. Regressions: `ZoneUnmeasuredTest` (six cases, including a `jogStartZone()` fixture that reproduces `i3-02-north`'s jog and asserts non-vacuously that the first match lands in the 100–200 m danger band), `qa/scenarios/edge/mid_zone_join.py`, and `qa/validate-zones.sh` 72/72 (which now reports "only ever Unmeasured" by name if the threshold is ever tightened too far)
- **Co-located camera handover**: the confirmation above is skipped when the candidate zone's start is within `COLOCATED_CAMERA_M` (250 m) of the end of the zone we just exited, for `COLOCATED_HANDOVER_MS` (30 s) afterwards, **and** the candidate continues the direction we finished the previous zone on (`continuesHandoverDirection` — the exited zone's local heading at its end vs the candidate's local heading at its start, within `RoadMatcher.DIRECTION_TOLERANCE_DEG`, both read over the ±150 m window so a start jog is averaged out rather than read literally). The direction clause is not optional: at a co-located camera the **opposite-carriageway sibling** also starts within 250 m — `trakiya-03-west`'s start is 15 m from `trakiya-03-east`'s end, which is also `trakiya-04-east`'s start — so proximity alone lets it claim the bypass and open a *measured* traversal of the zone running back the way we came, on a **single** wrong-bearing fix. And that fix is not hypothetical: `trakiya-04-east`'s stored centerline opens with a 19 m segment bearing west (ISSUE-001 again), so a route following the geometry genuinely reads as westbound for one fix at the seam. Symptom was a ~10-fix phantom traversal of the westbound sibling with a spoken entry, which then pushed the real successor's first match ~700 m in — past `START_WITNESS_ARC_M`, so it degraded to `Unmeasured`. Caught by `qa/colocated-zones.sh --all` (7/24 pairs); regression `ZoneUnmeasuredTest."the opposite-carriageway sibling cannot claim the co-located handover"` (verified to fail with the guard stubbed out) — having driven A to its end *is* the continuous-on-road evidence confirmation exists to gather. Keeps the `InZone(A) → Exiting(A) → InZone(B)` handover (and the chained exit/entry announcement `AudioAlertManager` drives from it) working at the 24 back-to-back pairs in the data. The window is not one-shot because A's exit fires up to `EXIT_DISTANCE_M` *before* the shared camera, and B only becomes the nearest zone once past it
- **Direction matching is local, not end-to-end**: `RoadMatcher.matchDirection` compares the fix course against the centerline's heading **in the neighbourhood of the fix** — `localPolylineBearing` over a ±`LOCAL_BEARING_WINDOW_M` (150 m) window — not `polylineBearing`'s single first→last bearing. On a 10–25 km zone that end-to-end bearing says almost nothing about which way the road runs at a given place: at Кочериново the A3's heading was 43–45° off the zone's end-to-end bearing (inside tolerance) while being 48–57° off the road's *local* heading. Reading it over a window rather than off the nearest single segment also absorbs the backwards endpoint jogs in the stored geometry (ISSUE-001, ≤122 m), which a bare nearest-segment bearing would misread as "driving the wrong way" at the zone start. Regression: `RoadMatcherTest."matchDirection uses the local heading, not the zone's end-to-end bearing"`
- **Off-ramp detection / off-road exit hysteresis**: an off-road fix (distance from centerline beyond the on-road band) no longer exits on the spot — the smoothed Kalman position lags off the road for a fix or two on a bend (worse on coarsely-sampled server centerlines), and momentary glitches (overpass, tunnel mouth, urban canyon) throw single fixes wide. The in-zone check uses the **zone-appropriate** band (motorway override 150 m, same as entry matching, not the old tight 100 m), and exit requires the off-road condition to persist `OFF_ROAD_EXIT_GRACE_FIXES` (3) consecutive fixes — *unless* the fix is `OFF_ROAD_HARD_M` (1000 m) past the road, a real departure that exits immediately. A genuine off-ramp diverges steadily and trips the streak in a few seconds. Caught by `qa/validate-zones.sh` (struma-02-north / trakiya-01-west / hemus-02-west flapped `InZone → Exiting → InZone` on the coarser **server** centerlines, while the aligned bundle passed); regression `ZoneDetectorTest."transient off-road blip does not exit, but sustained off-road does"` + `"…back on-road within the grace window…"`.
- **Reversed centerline / endpoint orientation**: `ZoneDetector` orients every zone's centerline to run `start → end` once at construction (`orientCenterlineToStart`), so all order-dependent geometry (direction matching, polyline projection, remaining distance, puck snapping) is correct regardless of the stored point order. A centerline stored **end-first** — a real server-data bug; the scraper's `align_centerline_to_endpoints` fixes the bundle, but the live `/api/zones` may still serve it and the device syncs that into Room — would otherwise flip the zone's apparent first→last bearing, so the app matches the **opposite-carriageway sibling** and reports an inverted "remaining" (observed live via `qa/feed-zone.sh 0` on `europa-01-north` → matched `europa-01-south`, the "red dot first"). The `start`/`end` endpoints are authoritative, so the engine recovers without depending on a server redeploy. **Do not** add this as a `by lazy` property on the `Zone` data class — `ZoneRepository` round-trips `Zone` through Gson and the lazy delegate field breaks (de)serialization; orient at the detector boundary instead. Regression `ZoneDetectorTest."reversed-centerline zone still enters the correct sibling (qa feed-zone 0 bug)"` + `"…reports a decreasing, non-inverted remaining"`; on-device `qa/validate-zones.sh --keep-online` (72/72 against the reversed synced data).
- **End-of-zone exit**: `EXIT_DISTANCE_M = 100` (straight-line to `zone.end`) — the average + remainder guidance stay live until the end camera is in sight. The detector orients the centerline to actually reach `zone.end` (see above); a polyline-remaining ≤ 0 backstop also covers the case where `zone.end` is offset from the road.
- **Distance source split**: the speed×time integrator (`distanceTraveled`) feeds *only* the average-speed numerator; everything position-related (remaining label, progress, max-for-remainder, exit, entry provenance) is derived from `projectOntoPolyline` against the centerline arc length (`polylineLengthMeters`), which is drift-free. This is why uneven simulated traces / noisy GPS speed can't fake a mid-zone exit or collapse the remainder to 0. Regression: `ZoneDetectorTest."dense short-segment zone is a single clean traversal"` + `qa/scenarios/edge/dense_centerline.py`.
- **Zone overlap**: some zones share roads at junctions — handle priority
- **U-turn / re-joining mid-zone**: a driver who leaves the road and rejoins the same zone part-way does **not** cross the entry camera on the way back, so the rejoin is `Unmeasured` — the first (real) traversal was already finalized on the off-road exit, and the rejoin adds no second History row. Before entry provenance this opened a *second* measured traversal averaged over the remainder, i.e. a junk row on top of the real one. Regression: `ZoneDetectorTest."re-joining mid-zone after an off-road exit is Unmeasured, not a second traversal"`. Separately, a point *past* the end on the same straight road must not re-admit the just-finished zone at all — that's the tail guard below.
- **Hooked centerline tail / end-of-zone re-admission**: `handleOutside` refuses any zone whose `remaining <= EXIT_DISTANCE_M` **or** `distanceToZoneEnd <= EXIT_DISTANCE_M` — we are finishing that zone, not joining it. The polyline-remaining clause alone is insufficient when a centerline hooks/overshoots at its tail: two of its legs then run within metres of each other near the end, so `projectOntoPolyline` can snap a just-exited point onto the *earlier* leg and report a large `remaining`, briefly re-admitting the zone we are exiting (`Exiting → InZone → Exiting` flap on the final ~100 m). Caught by `qa/validate-zones.sh` (11/72 zones flapped at the tail before the guard); see `qa/CLAUDE.md`. **This guard outlived the `midZone` branch it was written for** and is now applied unconditionally: with mid-zone admission gone the flap would simply have returned in a new costume, as `Exiting → Unmeasured → …` over the same final ~100 m.
- **Tunnels**: common on Struma motorway — handle gracefully

## Vehicle-type-aware speed limit

`ZoneDetector.update(point, vehicleType)` takes a `VehicleType` (`CAR`/`TRUCK`/`BUS`/`MOTORCYCLE`, default `CAR`) and passes `vehicleType.limit(zone.speedLimits)` into every `AverageSpeedCalc.calculate(...)`, so a user who sets `vehicle_type` to truck/bus/motorcycle gets that limit (motorcycle falls back to the car limit when a zone has none). The three fields are **licence classes**, not vehicle shapes — `speedLimits.bus` is BG TOLL's `BE,C1,C1E,D,D1,D1E,DE` value, covering bus, minibus, truck 3.5–7.5 t and anything towing a trailer, which is why the Settings rows are labelled for the class and there is no separate car-with-trailer type (it would resolve an identical limit). See the note on `SpeedLimits` in `Models.kt`. Each case owns a `setting` token (`car`, `truck`, `bus`, `motorcycle`) that equals the Swift raw value and is what gets persisted to settings and to history rows — never `name.lowercase()`, which would diverge from iOS's camelCase raw values for any multi-word case added later. Regression: `VehicleTypeTest` / `VehicleTypeTests.swift`. `LocationTrackingService` mirrors `SettingsRepository.vehicleType` into `currentVehicleType` via a `lifecycleScope` collector and threads it into the detector call. Regression: `ZoneDetectorTest."vehicle type changes effective limit"`. This was ported from the Swift core; the iOS `ZoneDetector.update(_:vehicleType:)` is the equivalent.

## History statistics (`HistoryStats.kt`)

Pure stats over a captured `SpeedSample(timestampMs, speedKmh)` series, feeding the app's **History** feature (app layer `HistoryRecorder` captures the series; core stays pure). `sustainedExtremes(samples, windowMs = 3000)` smooths with a centered moving-average window (O(n) two-pointer) and returns the min/max of the *smoothed* series, so a single GPS spike/drop can't become the reported top/low ("sustained for a few seconds, not a flake"). `downsample(samples, maxPoints = 500)` passes through when it fits, else bucket-averages into ≤500 points (a long zone at 1 Hz exceeds 500). `runningAverage(samples)` returns the cumulative time-average at each sample — the evolving series both platforms' `SpeedGraph` fills as a band (converges toward the final trip average, not a flat line). Tests: `HistoryStatsTest`, with a shared golden fixture at `src/test/resources/history/spike_suppressed.json` mirrored for the iOS Swift port.

## iOS engine parity

The Swift hand-port at `ios/Packages/SrednaBGCore/` tracks this engine's behavior: centerline orientation to `start → end` (`orientCenterlineToStart`), off-road exit hysteresis (`offRoadExitGraceFixes = 3` / `offRoadHardM = 1000`), entry confirmation (`entryConfirmDistanceM = 300` / `entryConfirmFixes = 2` / `entryConfirmMaxFraction = 0.25` / `entryConfirmTimeoutMs = 30_000`) with back-dated entry, **entry provenance (`startWitnessArcM = 200`) and the `ZoneState.unmeasured` case it produces**, the co-located handover (`colocatedCameraM = 250` / `colocatedHandoverMs = 30_000`, witnessed by construction, with the `continuesHandoverDirection` guard), local-window direction matching (`RoadMatcher.localBearingWindowM = 150`), dropout distance bridging, `exitDistanceM = 100`, polyline-arc-length remaining (`polylineLengthMeters`), the `distanceRemainingOverride` split, and vehicle-type-aware limits. The co-located-camera TTS case (`Exiting → InZone` announces entering the next zone) lives in `ios/.../AnnouncementPolicy.swift`, mirroring `AudioAlertManager.onZoneStateChanged` — which is also where both platforms make **every** transition into or out of `Unmeasured` an explicit `silent` decision rather than an unmatched pair. `ZoneUnmeasuredTest.kt` and `ZoneUnmeasuredTests.swift` are mirrored case-for-case, including the `jogStartZone()` fixture.
